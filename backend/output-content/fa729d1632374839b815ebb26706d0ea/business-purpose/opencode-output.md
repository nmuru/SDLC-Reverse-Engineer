{"phase":"business-purpose","documentation":"# Business Purpose — NetworkPro (CareerPro-v2)\n\n## 1. Purpose Statement\n\nNetworkPro is a career and networking web application whose purpose is to turn a professional's LinkedIn profile into a personalized, guided career-development plan. A user uploads their LinkedIn profile as a PDF; the application extracts the profile details and then walks the user through a four-stage workflow — profile review, career-interest selection, networking recommendations, and job/learning recommendations — producing concrete, saveable suggestions of people to follow, people to connect with, jobs to pursue, courses to take, and skills to develop.\n\nAs implemented today, the repository is a **functional product prototype**, not a production service. The end-to-end user experience is fully built and self-consistent, but the intelligence behind it is simulated: PDF text extraction returns a fixed demo profile, all recommendation content is mock data defined in the API layer, persistence is in-memory, and every request is attributed to a single hard-coded demo user. The business purpose is therefore best stated as: **demonstrate and validate the product concept of an AI-assisted career-growth assistant for individual professionals, using a complete clickable experience backed by simulated data.**\n\n## 2. Problem the Software Addresses\n\nThe system addresses the difficulty individual professionals face in turning a static LinkedIn profile into actionable career progress:\n\n- **Profile without direction** — professionals have profile data but no systematic way to convert it into next steps for their career.\n- **Networking without focus** — deciding whom to follow or connect with on a large professional network is unstructured; the product proposes relevant people and content instead.\n- **Job search without fit signal** — job boards provide no personalization; the product frames openings with match percentages tied to the user's profile and stated goals.\n- **Skill development without market context** — the product proposes which skills to learn next and which courses to take, framed against market demand (e.g., \"High Demand\", \"+28% higher salary with this skill\").\n\nThe design deliberately avoids LinkedIn OAuth integration in favor of PDF upload as the ingestion mechanism, which the project brief records explicitly: users \"upload their LinkedIn profile as a PDF (instead of OAuth authentication for now)\" (`attached_assets/Pasted-Project-Title-NetworkPro-Overview-...txt`). This positions the tool as a lightweight, no-integration career assistant that works from an export the user already has.\n\n## 3. Who It Serves\n\n- **Primary users: individual professionals and job seekers** — knowledge workers managing their own career growth. The UI speaks directly to this audience (\"Elevate your career…\", \"Your Journey to Career Success\", testimonials from a UX Designer and a Data Scientist in `client/src/pages/HomeTab.tsx`).\n- **Demonstrated persona: product-management-track professionals in tech.** The demo profile (\"Senior Product Manager at TechCorp\"), the mock job listings (PM roles at Google, Salesforce, Airbnb, Microsoft, Netflix), courses, and skill suggestions are all concentrated on this career path. This is the showcase persona for the prototype; the product concept itself is career-generic (career-goal selectors include Healthcare, Finance, and Education industries).\n- **Operators/audience of the artifact:** the README describes the project as a one-shot Replit-built demo deployed to Vercel with an MIT license, and the repository contains Replit tooling (`@replit/vite-plugin-cartographer`, `theme.json`). The current audience is reviewers, collaborators, or the creator's own evaluation of the concept rather than end customers at scale.\n- **Non-users:** there is no multi-tenant, organizational, recruiter-facing, or B2B surface anywhere in the code. Every API route hard-codes `userId = 1` and no authentication exists, so no real per-user population can be served in the current state.\n\n## 4. Outcome the User Obtains\n\nA user completing the workflow obtains:\n\n1. A **structured view of their professional profile** (name, headline, location, industry, current role/company, experience, education, skills) extracted from the uploaded PDF, with manual editing available (`ProfileCard`, `ProfileEditor`).\n2. A **confirmed set of career interests** — suggested topics and skills pre-selected from the profile, plus custom additions, persisted as the basis for later recommendations (`InterestsTab`, `POST /api/interests`).\n3. **Networking recommendations** — five people to follow, five people to connect with, and trending posts, each saveable for later (`NetworkingTab`, `GET /api/recommendations/networking`).\n4. **Career-opportunity recommendations** — job openings with match percentages and salary ranges, recommended courses, and skills to develop, filtered by the user's declared career goals (desired role, industry, location, salary range) (`JobsTab`, `GET /api/recommendations/jobs`, `POST /api/career-goals`).\n5. A **personal shortlist** — any person, job, course, post, or skill can be saved or removed via the saved-items capability (`POST/GET/DELETE /api/saved-items`), wired into all five recommendation card components.\n\nToday these outputs are demonstrative rather than genuinely personalized: the recommendation generators ignore the profile and interests they receive, and the extracted profile is a fixed sample. The outcome the product *intends* to deliver — and demonstrates the shape of — is a tailored action plan for career growth.\n\n## 5. Core Domain Concepts\n\nThe domain model, evidenced by `shared/schema.ts`, `client/src/types/index.ts`, and the API contracts, reveals the problem being managed:\n\n| Concept | Meaning in the workflow |\n|---|---|\n| **Profile** (LinkedInProfile) | The user's professional identity: headline, location, industry, current role/company, experience, education, skills, certifications. The raw material for all recommendations. |\n| **Interests** | Topics and skills the user wants to follow or learn; the declared preference layer between profile and recommendations. |\n| **CareerGoals** | Desired role, industry, location, and salary range; the target state the user is aiming for. |\n| **Networking recommendations** | People to follow, people to connect with, trending posts — the social-capital dimension of career growth. |\n| **Job recommendations** | Job openings (with match %, salary, applicants), courses (with provider, rating), skills to develop (with market-demand claims) — the opportunity dimension. |\n| **SavedItem** (person, job, course, post, skill) | The user's personal shortlist; the system's unit of \"act on this later.\" |\n| **User** | Account holder; currently a single hard-coded demo identity. |\n\nThe relationships — Profile → Interests → Goals → (Networking + Job recommendations) → SavedItems — are precisely the funnel of a career-coaching product: know who you are, state what you want, receive who/what/where to engage, and keep a shortlist.\n\n## 6. Representative End-to-End Workflow (Traced)\n\nThe central workflow, traced from UI entry point through API to outcome:\n\n```mermaid\nflowchart LR\n    subgraph Client [React SPA - tab wizard]\n        A[HomeTab: upload LinkedIn PDF] --> B[\"Analyzing Your Professional Profile\" state]\n        B --> C[ProfileCard: extracted profile + edit]\n        C --> D[InterestsTab: suggested topics/skills]\n        D --> E[NetworkingTab: people to follow/connect, trending posts]\n        E --> F[JobsTab: career goals form + jobs, courses, skills]\n    end\n\n    subgraph API [Express API - server/routes.ts]\n        G[\"POST /api/profile/upload\\n(multer, PDF-only, 5MB)\"]\n        H[\"GET /api/interests/suggestions\\nPOST /api/interests\"]\n        I[\"GET /api/recommendations/networking\"]\n        J[\"GET /api/recommendations/jobs\\nPOST /api/career-goals\"]\n        K[\"POST /api/saved-items\"]\n    end\n\n    subgraph Backend [server internals]\n        L[\"extractTextFromPdf\\n(simulated - fixed demo text)\"]\n        M[\"extractProfileFromText\\n(regex heuristics)\"]\n        N[\"Mock generators: people, posts,\\njobs, courses, skills\"]\n        O[MemStorage - in-memory Maps\\nfixed userId = 1]\n    end\n\n    A --> G --> L --> M --> O --> C\n    D --> H --> O\n    E --> I --> N\n    F --> J --> N --> O\n    F --> K --> O\n```\n\nStep-by-step:\n\n1. **Ingestion** — the user selects a PDF in `FileUploader`; `useLinkedInProfile` posts it to `POST /api/profile/upload` (`client/src/lib/pdf-parser.ts`). The server accepts only `application/pdf` up to 5 MB (multer config, `server/routes.ts`).\n2. **Extraction (simulated)** — `extractTextFromPdf` does not parse the uploaded file; it logs \"Simulating PDF extraction\" and returns a fixed sample LinkedIn profile text. `extractProfileFromText` then applies simple regex heuristics (name/headline/location/industry/role/company/skills/education/experience) to that text, falling back to placeholder values when sections are absent.\n3. **Profile persistence** — the extracted profile is stored in `MemStorage` under the fixed demo user (create-or-update on `userId = 1`) and returned to the client, which renders `ProfileCard` with an edit path (`PUT /api/profile`).\n4. **Interest capture** — `InterestsTab` fetches suggested topics/skills (`GET /api/interests/suggestions`), lets the user toggle and add custom interests, and saves them (`POST /api/interests`). The suggestion function currently returns a fixed set regardless of the profile.\n5. **Networking recommendations** — `NetworkingTab` fetches `GET /api/recommendations/networking`; the server returns hard-coded people-to-follow, people-to-connect-with, and trending posts. \"Follow\" and \"Connect\" actions surface confirmation toasts only; nothing is sent to any external network. Every card offers Save for Later via `POST /api/saved-items`.\n6. **Job/learning recommendations** — the user records career goals in `JobsTab` (`POST /api/career-goals`, with Product-Manager-in-Tech defaults when none exist) and fetches `GET /api/recommendations/jobs`, which returns hard-coded job openings, courses, and market-demand skill suggestions, each saveable.\n7. **Outcome** — the user leaves with a reviewed profile, declared interests and goals, and a saved shortlist of people, jobs, courses, posts, and skills — the complete product experience, executed against simulated intelligence and non-durable storage.\n\nThis workflow explains why every major component exists: the tab wizard implements the guided funnel; the API layer exists to shape the eventual real recommendation service; MemStorage and the mock generators exist to make the funnel fully traversable before any real data source, AI model, or database is attached.\n\n## 7. Documented Intent vs. Implemented Reality\n\nMaterial discrepancies that affect how the purpose should be read:\n\n1. **README says there is no backend; the repository contains one.** The README states \"Currently does not have any backend - vercel deployed frontend,\" yet `server/` contains a full Express application with ten working API routes, and `package.json` defines `dev`/`build`/`start` scripts that run it. The client exclusively consumes these server endpoints (`pdf-parser.ts`, `useSavedItems.ts`, `useRecommendations.ts`). The README statement is accurate only for the Vercel hosting arrangement (a static frontend deployment; no `vercel.json` or server deployment config exists in the repo) and is misleading about the system itself.\n2. **\"AI-powered\" is a product claim, not an implemented capability.** The UI and README repeatedly describe AI-driven analysis and recommendations, and the loading screen says \"Our AI is processing your LinkedIn data.\" No ML/NLP library, model API key, or inference code exists anywhere in the repository; the closest implementation is basic regex extraction plus fixed suggestion lists. The intelligence is aspirational; the wiring for it (separate extraction and recommendation services) is scaffolded.\n3. **Database declared but unused at runtime.** PostgreSQL schemas (Drizzle), `drizzle.config.ts` (requiring `DATABASE_URL`), `@neondatabase/serverless`, and `connect-pg-simple` are present, but the server instantiates `MemStorage` and never imports a database client. Persistence today lasts only for the process lifetime. The README's \"Database: PostgreSQL with Drizzle ORM\" describes intent, not current runtime behavior.\n4. **Planned features absent from implementation** (per the brief vs. code): recruiters-to-connect-with recommendations, an \"Experts to Consult\" category, an \"Ignore/dismiss\" action, and \"Apply\"/\"Connect\" integrations with real targets. Follow/Connect/Apply actions currently produce toast confirmations only.\n5. **Implemented but undocumented**: the client contains a complete localStorage persistence module (`client/src/lib/storage.ts` with `networkpro-*` keys) that nothing imports — an alternative persistence path that was built and then abandoned in favor of the API-backed saved-items flow.\n6. **No tests exist** anywhere in the repository, so no behavior is independently verified; the workflow description above rests on source and wiring evidence.\n\n## 9. Conclusion\n\nNetworkPro exists to convert a professional's LinkedIn profile into a personalized, actionable career-growth plan — networking targets, job opportunities, learning resources, and skill priorities — through a guided four-step experience.
